# Tailwind components

## Status

Accepted V1 workflow for supported Tailwind React components.

## Purpose

ORC-web can import a supported React component that uses complete Tailwind class strings, render it faithfully in the live editor, make limited reliable visual edits, and export the React and Tailwind source without flattening it into unrelated CSS.

This is a source-preserving workflow.
It does not treat Tailwind as a second design system beside HTML, CSS, SVG, and the canonical document.

## Supported V1 path

1. Import inspection reads the React or JSX source, Tailwind class strings, required stylesheets, theme inputs, assets, and package dependency information.
2. The importer accepts the component only when its source and Tailwind inputs fit the supported contract.
3. The local render pipeline runs the Tailwind compiler for the accepted source and supplies the generated CSS to the browser editor.
4. The editor renders the live React component with its generated CSS beside ordinary HTML, CSS, and SVG content.
5. Code Apply or an MCP source update recompiles the candidate source before it becomes the new committed revision.
6. React plus Tailwind export preserves the accepted component source, required Tailwind inputs, managed assets, and dependency information.

The compiler output is rendering support for the browser.
The saved project keeps the accepted authored source and required inputs instead of storing only generated CSS.

## Style scope

Imported component styles apply only within their intended design scope and the component descendants that use them.
They do not restyle the ORC-web interface or unrelated top-level frames.
Components and frames can share a token or a component record only through an explicit design reference.

The exact CSS isolation mechanism is an implementation decision.
The accepted product behavior is that importing one design cannot unexpectedly change another design's appearance.

## Base UI and shadcn

Base UI is unstyled and does not require Tailwind in order to render as a supported component.
Base UI-flavored shadcn components commonly carry Tailwind class strings and can use this Tailwind workflow when the imported source is otherwise supported.

V1 recognizes the accepted Base UI import paths and supported API or render-prop shapes.
V1 does not recognize Radix import paths as editable-component contracts.
The import result explains the supported or unsupported boundary before it changes the project.

## Visual editing of static classes

Properties can edit a Tailwind-backed value only when a source binding identifies a complete static class string or a declared component property that owns it.
For example, a supported color, gap, radius, text, or sizing control can replace its own static utility with another valid utility.

The edit preserves unrelated classes, including responsive, hover, focus, dark-mode, and other variant classes.
It does not reorder or rewrite them merely because a person changed one visual value.
The command validates the candidate source and recompiles it before committing one new document revision.

A visual edit that cannot preserve the authored source safely is unavailable with an **Edit source** explanation.
ORC-web does not generate a guessed class string or an unrelated inline style as a substitute.

## Dynamic-class limit

Tailwind detects complete class names in source.
V1 therefore does not visually rewrite dynamically constructed class expressions, arbitrary template fragments, or classes generated by unsupported code.

Those components can remain source-editable when they render successfully.
They do not claim the same reliable visual Tailwind editing path.
The future work list is in [Tailwind source workflow beyond V1](../../backlog/tailwind-source-workflow.md).

## Theme, styles, and packages

The accepted import records the Tailwind stylesheet and theme inputs needed to generate the component's visual result.
It records exact component dependencies and managed assets with the project bundle.

An import that requires an unsupported custom plugin, arbitrary project-wide CSS, environment data, or another unavailable build input reports that requirement during inspection.
It does not silently render with missing styles or a different theme.

The exact supported Tailwind configuration surface is an implementation acceptance task.
The V1 product rule is that an accepted component must reopen and render from the saved project without relying on a mutable package registry or the original machine's global cache.

## Code, MCP, and export

The Code window shows the applied Tailwind source for the selected scope and keeps unfinished edits only in the current editing session until Apply.
An agent uses `get_context` or `get_source` to read the current applied source, then applies a mutation through the same command engine.

React plus Tailwind export preserves supported authored class strings whenever they already express the design.
For ordinary ORC-web design objects that do not begin as Tailwind source, export generates readable Tailwind utilities from canonical design values and tokens.
If a supported utility cannot preserve a design value faithfully, export includes supporting CSS rather than changing the appearance.

HTML, raw CSS, SVG, image, and PDF export remain available according to [Export](export.md).
Static HTML export explains when a selected live component cannot be represented faithfully.

## V1 boundary

V1 supports accepted React components with complete static Tailwind classes, retained styles and theme inputs, local compilation for live rendering, limited reliable visual class edits, Code and MCP source updates, and faithful React plus Tailwind export.

It does not promise full compatibility with dynamic expressions, custom plugins, arbitrary project configuration, or arbitrary package CSS.
